Olinea documentation

Olinea is a USDC vault on Arc whose releases are authorized by SLH-DSA-SHA2-128s (FIPS 205) signatures verified on-chain by Arc's post-quantum precompile. There is no owner, no admin key, no pause and no upgrade path.

Overview

The vault holds USDC through the ERC-20 interface at 0x3600000000000000000000000000000000000000 and releases it only when a 32-byte hash-based verifying key fixed at deployment authorizes the transfer. The verifying key is not an elliptic-curve key, so a quantum computer that breaks ECDSA cannot forge a release.

Two details are load-bearing, and both are easy to get wrong:

  1. The precompile returns false for a forged signature without reverting. A contract that checks only whether the call succeeded accepts every forgery. See Security model.
  2. The signed message binds everything. The key signs exactly keccak256(abi.encode(chainId, vault, to, amount, nonce)), so an authorization cannot be replayed on another chain, in another vault, for another recipient or amount, or twice in the same vault. See Authorization digest.

Quickstart

Everything that touches the real precompile costs nothing and needs no wallet: verification is a read call, so you can check the vault's authorization path against Arc mainnet before you deploy anything. 

# the vault and its test suite
git clone https://github.com/thesithunyein/olinea
cd olinea/contracts && forge test            # 17 tests

# post-quantum tooling
cd ../scripts && npm install
node pq.mjs keygen                            # SLH-DSA keypair -> scripts/keys/pq-key.json
node pq.mjs conformance                       # real mainnet precompile, no wallet

Keep the key. keygen writes the secret key to scripts/keys/pq-key.json, which is gitignored. Lose it and any funds in a vault built on it are unrecoverable — there is no admin escape hatch.

Authorization digest

The signing key never touches the chain. It signs one 32-byte digest per release:

digest = keccak256(abi.encode(block.chainid, address(vault), to, amount, nonce))

Because all five values are inside the digest, a signature is valid for exactly one release: moving it to another chain changes chainid, moving it to another vault changes the vault address, and replaying it in the same vault fails on the consumed nonce. Nonces are per-vault and need not be sequential — they only have to be unique.

The digest is passed to the precompile as the message with no additional hashing by the caller: the vault passes abi.encodePacked(digest), 32 bytes.

When it reverts

Only malformed input reverts: Input too short, Invalid selector, Invalid verifying key length, Invalid signature length. A cryptographically invalid signature is a value, not an exception, and that asymmetry is the entire footgun.

Calling it correctly

// WRONG — true for every forgery
(bool ok, ) = PQ.staticcall(data);
require(ok, "verify failed");

// CORRECT — decode the boolean the precompile returned
(bool ok, bytes memory ret) = PQ.staticcall(data);
require(ok && ret.length == 32 && abi.decode(ret, (bool)), "invalid PQ signature");

The precompile lives in Arc's execution layer rather than in upstream EVM, so calling it in a local test suite requires Arc Foundry (arc-anvil --network arc), whose prebuilt binaries currently cover Linux and macOS (Apple Silicon) only. Olinea's suite therefore injects the verifier and proves the real precompile against mainnet instead.

Units on Arc. USDC is exposed twice on one balance: natively with 18 decimals for gas, and through the ERC-20 interface at 0x3600000000000000000000000000000000000000 with 6 decimals for transfers. Mixing them is a 1012 error. Olinea only ever uses the 6-decimal view; gas is 2 × 10⁻⁸ USDC per gas unit.

CommandWhat it does
keygenGenerates an SLH-DSA-SHA2-128s keypair and writes it to scripts/keys/pq-key.json
authorizePrints the digest and the signature for one release, plus a ready-to-run cast send line. --check verifies the signature against the live mainnet precompile
conformanceRuns three cases — valid digest, tampered signature, different digest — against the real precompile. Exits non-zero on any failure, so it works as a pre-deploy gate

Set ARC_RPC to point at a different Arc endpoint; the default is https://rpc.drpc.mainnet.arc.io, since Arc's own RPC hosts are not reachable from every jurisdiction.

Security model

What the contract guarantees:

  • One key, nothing else. No owner, no admin, no pause, no upgrade, no delegate. There is no code path that moves USDC except a valid post-quantum authorization.
  • Listed in the digest. Chain id, vault address, recipient, amount and nonce are all signed, so an authorization is bound to a single release.
  • Nonces are consumed before the transfer, so a valid authorization cannot be replayed even by re-entering the same transaction.
  • Verification is on-chain. No oracle, no committee, no off-chain signer and no trusted relayer: the relayer pays gas and gets nothing.
  • A forgery is not a revert. The vault decodes the returned boolean, and the test suite includes NaiveVault.sol — the same vault with the "call succeeded" bug — to prove it drains on a forgery while OlineaVault does not.

What it does not do:

  • It does not make the vault's USDC denylist-resistant — see below.
  • It does not protect a compromised signing device. The key is the authorization; sign only what you mean to sign.
  • It does not recover funds.

Limitations

Unaudited. The contracts are new code. The test suite and mainnet evidence are the assurance available today, and that is not a substitute for review. Do not put amounts you cannot lose into an unaudited vault.

  • No recovery. Lose the post-quantum key and the funds are unrecoverable by design. That is the property, not an oversight — it is also why there is nothing for an attacker to phish.
  • Circle's denylist still applies. A forged SLH-DSA signature cannot move funds, but the USDC token itself can still block transfers. Post-quantum authorization is not denylist resistance.
  • Verification is not free. 382,879 gas per release, ≈ $0.0077 at Arc's 20 Gwei base fee — small, but roughly 1,300× a plain USDC transfer on the same chain.
  • Signatures are large. 7,856 bytes posted as calldata per release. That is the price of hash-based signatures; it is not compressible.
  • Signing is slow by design. SLH-DSA-SHA2-128s is tuned for small keys and conservative assumptions rather than speed — expect seconds, not milliseconds, per signature.

Deploying a vault

Deploying is a one-shot sequence, and step 1 is free: generate the key and check its digest against the live precompile before anything is on chain. You need a funded Arc account for steps 2 onwards — gas is paid in USDC. 

export ARC_RPC=https://rpc.drpc.mainnet.arc.io
export ARC_PRIVATE_KEY=0x..                    # a few USDC for gas
USDC=0x3600000000000000000000000000000000000000

# 1. key + conformance (free, no wallet)
cd scripts && node pq.mjs keygen && node pq.mjs conformance

# 2. deploy (verifier = address(0) -> the real precompile)
cd ../contracts && forge create src/OlineaVault.sol:OlineaVault \
  --rpc-url $ARC_RPC --private-key $ARC_PRIVATE_KEY --broadcast \
  --constructor-args $USDC 0x<your-32-byte-vk> 0x0000000000000000000000000000000000000000

# 3. fund it
cast send $USDC "approve(address,uint256)" $VAULT 2000000 --rpc-url $ARC_RPC --private-key $ARC_PRIVATE_KEY
cast send $VAULT "deposit(uint256)" 1000000 --rpc-url $ARC_RPC --private-key $ARC_PRIVATE_KEY

# 4. authorize a release (prints the signature and a cast send line)
node ../scripts/pq.mjs authorize --vault $VAULT --to $RECIPIENT --amount 250000 --nonce 1 --check

# 5. verify the vault's balance afterwards
cast call $VAULT "balance()(uint256)" --rpc-url $ARC_RPC

The verifying key is immutable. Deploy a new vault to change keys, and treat the deployed key as the whole security boundary from the moment the first USDC lands.
